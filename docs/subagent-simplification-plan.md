## 1. 目标与完成条件

主 Agent 能拿到准确的任务身份、执行状态和结果，自主安排任务、顺序、进度与验收；子 Agent 在任务范围内自主完成工作并返回结果；插件提供可靠的执行和通信。

本轮完成后应能观察到：

1. 创建没有名称的后台任务后，主模型立即从工具正文取得任务 ID，并据此补充消息或停止任务。
2. 审查角色可以运行合理检查，包括产生临时文件的检查；正式交付文件的修改由主 Agent 安排给实施者。
3. 角色、任务、轮次的含义一致；展示摘要和执行输入各有明确来源；旧记录仍然可以读取和续接。
4. 前后台、续接、停止、保存和通知的现有可靠性保持，测试覆盖主模型真正能看到的信息。

沿用单工作目录、Pi 原生 Session、三个公开工具以及当前 v3 记录格式。Jev 继续只选择模型和思考强度。业务完成与验收由主模型判断，运行时只记录执行事实。

## 2. 实施前核对的问题与证据

## 3. 数据含义与兼容选择

### 身份

| 概念 | 内部名称 | 生命周期与职责 |
| --- | --- | --- |
| 角色 | `roleId` / `AgentDefinition.id` | 可复用职责、工具与扩展配置 |
| 任务实例 | `runId` | 从创建到多次续接保持稳定；`instanceName` 是可选寻址别名 |
| 执行轮次 | `turnId` | 每次执行更新，用于结果、通知和迟到事件归属 |
| Pi 上下文 | `childSessionId / childSessionPath` | 保存真实对话；同一任务续接时复用 |

内部继续使用 `runId`，不开展全仓命名迁移。公开 `agentId`、`task_id`、`resume` 和 `to` 保持兼容，在接口边界解析或投影到内部任务身份。历史 `legacy.agentId` 可能表示旧角色身份，不能按名称批量替换为任务 ID。

### 文本

| 字段 | 约定 |
| --- | --- |
| `description` | 本轮短标题；调用方提供时优先，否则由本轮任务要求派生 |
| `instruction` | 主 Agent 本轮明确提交的完整任务要求 |
| `objective` | 为兼容 v3 保留的派生展示摘要，由同一个摘要逻辑生成 |
| `RunnerRequest.prompt` | 供执行使用的输入，续接时可以包含待消费补充消息与本轮要求 |
| Pi Session 消息 | 实际送入子模型的消息与工具记录的事实来源 |

`instruction` 与 `RunnerRequest.prompt` 不能直接视为冗余副本：当前续接会将暂存消息加入请求，启动过程中到达的消息还可能在执行边界加入。统一的是生成责任，消息消费顺序和次数保持原有语义。

当前状态、每轮结果快照、Pi Session 各自服务实时查询、历史查询和真实上下文；本轮保留它们。执行状态与进程资源状态继续分别表达，避免把“模型结束”误认为“进程已退出”。

## 4. 实施顺序

顺序：基线核对 → P1 回执修复 → P2 提示词收敛 → P3 数据整理 → P4 整体验证。每阶段先完成自己的验收，再进入下一阶段。

### P0：核对实施基线

- 读取当前 `DEVELOPMENT.md`、本计划、工作区修改及现有检查结果。
- 保存实际基线提交、文件差异和必要恢复材料；已有修改继续保留在当前目录。
- 如果仍是已经验证过的同一代码基线，可以引用本会话的修改前结果；代码发生变化或换了执行环境时重跑适用检查。

完成条件：能区分原有改动、本轮改动和已存在的失败。恢复操作只针对本轮修改。

### P1：让模型可见的回执包含调度所需信息

主要文件：`src/tool-contract.ts`、`src/index.ts`、`src/delivery.ts`；测试重点为 `test/claude-interface.test.ts`、`test/delivery.test.ts`、`test/rpc-integration.test.ts`。

1. 在统一回执生成入口，为三个工具返回简短的任务身份和当前状态。保留 `details` 给界面及记录使用，模型后续操作需要的信息同时写入 `content`。
2. 正文至少包含稳定任务 ID、可选实例名称、当前状态和本次操作说明。消息回执明确 queued/deferred 的含义；失败或停止未确认时保留原因。模型尚在选配时只报告已知事实。
3. 最终文本、错误证据沿用现有交付路径。协调 `taskOutput()` 与工具回执的标题，避免重复添加任务头；不把完整 `RunDetails` 序列化到模型上下文。
4. 快速结束的后台任务继续直接返回最终结果，并沿用已有通知去重。通知正文与工具回执表达同一任务身份。

后台启动回执示意，具体排版可由实施者选择：

```text
agentId: A-12345678
状态：运行中
本轮在后台执行。可用此 agentId 调用 SendMessage 或 TaskStop。
完成结果将通知当前仍活动的所属父会话。
```

关键验收：

- 不指定 `name` 创建后台任务，仅从返回 `content` 提取 ID，随后用它执行 `SendMessage` 与 `TaskStop`，确实作用于该任务。
- 分别覆盖有名称、选配中、普通后台、快速终态、前台、显式 resume、失败、停止未确认；正文中的身份和状态与实际任务一致。
- 同时发起两个无名称后台任务，从各自正文取得不同 ID；补充或停止其中一个不会操作另一个。
- 经当前安装 Pi 的模型消息转换路径后，ID 仍出现在模型输入中。增加本地受控父模型/provider 场景，证明下一轮可从收到的正文取得 ID 并发起控制调用；该场景不读取 `details` 代替模型，不使用在线账号。
- 既有通知去重、最终文本保留、失败信息及资源释放测试保持通过。

这一步可以独立交付；数据整理不应成为修复调度缺陷的前置依赖。

### P2：缩小角色限制，明确主模型的协调责任

主要文件：`agents/reviewer.md`、`agents/scout.md`、`agents/worker.md`、`src/instruction.ts`、`src/index.ts` 的 Agent 工具描述。

- reviewer/scout 负责调查、检查和返回证据。允许任务相关的 Bash、测试及必要临时产物；源码、项目配置等正式交付文件的修改交由实施者处理。
- 检查如果会自动修复源码、更新快照或改写锁文件，属于实施工作，由主 Agent 安排；缓存、临时报告不自动被当作正式文件修改。
- worker 在目标范围内自主决定实现方法和合理验证。保留用户或委派任务已明确给出的范围和约束，删去容易暗示“每条普通检查都要额外授权”的泛化措辞。
- 主模型安排同一目录中的正式文件修改，主模型自己也计入实施者。审查/调查可以并行；需要稳定代码版本的检查由主模型安排在适当时机。
- 子 Agent 在范围内自主处理；缺少关键决定时返回已完成内容、阻塞原因和所需决定。结果使用自然文本，由主 Agent 验收。

保持 reviewer/scout 的 `disallowedTools: [edit, write]`，使用 Pi 原生工具与扩展选择。行为约定放在对应角色和简短调度说明中。

完成条件：角色职责与开发文档一致；审查角色保有 Bash 和必要检查能力。复用已有真实 Pi 本地扩展检查验证工具可用性；提示词的行为改善需要实际模型试用才能证明，不以字符串断言或受控 provider 冒充。

主要文件：`src/types.ts`、`src/tool-contract.ts`、`src/index.ts`、`src/runtime.ts`、`src/persistence.mjs`、`src/persistence.d.mts`；按实际引用调整显示与测试。

3. 把 `LegacyAgentReport`、`LegacyRunView`、旧状态类型移到专门的 `legacy-types.ts`，必要时在原位置保留类型导出兼容。类型隔离即可，不拆成新的兼容服务。
4. 继续由 `adaptStoredRun()` 集中处理 v1/v2/v3 读取，保留历史内容和按需续接迁移；当前运行逻辑使用现行字段。

完成条件：

- 新建与续接的标题、摘要、完整要求按同一约定生成，长文本和多行文本没有被摘要替代。
- 续接前暂存两条补充，再提交本轮要求；检查真实子会话收到的消息顺序和消费次数，补充信息不丢失、不重复。
- 同任务 ID/Session 保持，轮次更新；角色文件修改后，续接仍使用创建时配置。
- 旧记录能查看与续接；启动扫描不批量改写历史；当前轮结果不被旧报告覆盖。
- 核心类型文件主要呈现现行模型；没有新增另一套任务、报告或业务验收状态。

## 5. 必须保留的运行事实

- 同一任务的输入序列化、轮次归属、父会话寻址与通知去重。
- Pi 原生执行循环、工具/扩展配置及创建时配置快照。
- 结果保存错误、进程清理错误和“停止未确认”的真实表达。
- 正常结束与业务验收分离，`completed` 仍只表示本轮正常结束。
- `SendMessage` 补充信息，显式 `Agent({ resume, prompt })` 启动下一轮。

本轮保留现有的通知范围：后台自动通知针对当前进程中仍活动的所属父会话；切换或重载后的结果可从持久记录查看。跨重载补送、主动状态查询等需求留待独立讨论，避免顺带扩成调度平台。

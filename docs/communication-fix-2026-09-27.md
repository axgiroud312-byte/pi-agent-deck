## 修改后的流程

```text
主 Agent 派发
  → 子 Agent 执行
  → 有关键疑问：SendMessage(main, wait_for_reply=true)
  → 主 Agent 收到问题并回答
  → 原子进程、原调用栈、原会话继续
  → 正常收尾仍有补充：取回队列消息，在原轮次继续
  → 完整交付，释放进程
  → 主 Agent 验收，必要时 SendMessage 续接原会话
```

- 父 `SendMessage` 根据目标状态处理：运行中 `queued`、等待中 `answered`、结束后 `resumed`。显式 `Agent.resume` 复用相同续接实现。
- 子 `SendMessage` 使用 Pi RPC 的原生 UI 请求/响应通道，保留请求编号关联回答。当前问题只用可选 `pendingQuestion: { id, message }` 表达，完整问答继续由 Pi Session 保存。
- 前台遇到问题先交还主 Agent 控制权；回答后继续执行，最终结果自动通知。普通进度独立发送。
- `reply_to` 防止过期回答或重复回答被当成新一轮任务。等待中支持停止；孤立进程恢复检查清除已失效的当前问题。
- 角色显式工作工具白名单自动附加通信工具。工具 AbortSignal 可取消等待。
- 每轮的交付文本按顺序保留，后续摘要追加。历史通知正文保持原样，以 `turnId` 识别轮次。
- 内置 worker、scout、reviewer 正文各一句职责；角色生成模板同样保持简短。任务范围写在派发内容，公共通信说明集中维护。
- 后台回执说明如何等待自动通知。主 Agent 可以处理独立工作，当前只需等待时结束本轮回复，结果会自动唤醒它。

## 后续优化：消息、报告与收尾交接

本阶段参考 ZCode 的消息入队、原生输入证据和结果文件处理方式，保留现有模型编排与简短角色说明。增加的消息头用于定位任务、轮次、消息和报告；它们不规定角色行为，也不要求模型调用新的确认工具。

### 消息消费有据可查

双向 `SendMessage`、问题与结果交付保存到任务目录的 `messages.json`，记录稳定 ID、方向、轮次、正文、状态、创建/更新时间、可选提交时间与原因。新任务的完整派发要求继续由任务记录和原生子会话保存。

| 状态 | 可确认的事实 |
| --- | --- |
| `pending` | 消息已经保存，尚无消费证据；`submittedAt` 标记投递尝试，不单独证明接收成功 |
| `consumed` | 原生输入事件或会话记录证明消息进入接收方上下文 |
| `closed` | 因停止、问题结束等原因关闭，并保留原因 |
| `unknown` | 已有投递尝试，但恢复核对无法确认消费 |

提交回执不等于消费，进入上下文也不等于模型理解正确或完成任务。业务结论继续由主 Agent 根据交付验收。

父 `SendMessage` 通过父会话 ID 和原生 `toolCallId` 派生消息 ID。同一次工具调用重试返回 `delivery: existing` 与已有状态，避免再次投递；新工具调用即使正文相同，仍保存为独立消息。运行时根据 `user / toolResult / custom` 输入事件与原生 `message / custom_message` 记录确认消费，assistant 在回答中引用编号不算确认。

恢复时先读取原生父/子会话核对消息，原会话记录保持原样。未提交消息保持待消费；已经提交但没有证据的消息标为待核实。自动补投只用于尚未提交且仍有效的父会话结果、当前问题或活动轮次进度；已提交但不明确的消息不盲目重放。剩余待消费、待核实消息会提供数量与记录路径，供主 Agent 判断。

主 Agent 明确续接原任务时，确定尚未提交的子方向消息按原顺序带入新轮次。停止时关闭的消息若后来找到原生消费证据，可纠正为已消费。

### 每轮完整结果直接可读

每轮结果 JSON 旁自动生成相同 basename 的 Markdown 报告，保留完整交付文本和运行失败原因。先原子保存 Markdown，再写包含绝对 `reportPath` 的结果 JSON，两者成功后才发布路径。保存失败会进入运行错误，不返回虚假的报告地址。

工具回执和结果通知均提供报告路径。通知的 24,000 字符上限仅作用于预览，截断后的正文仍附完整路径。续接使用新的轮次文件，上一轮报告保留；重复保存已经存在的轮次结果时复用原文。旧 JSON-only 记录保持兼容，在显式保存时从历史快照生成可读报告。

### 补充消息与结束交接

正常收到 `agent_settled` 后，运行时在同一任务控制队列中检查状态、调用 `clear_queue` 取回未消费输入，并再次核对执行是否恢复。有剩余消息时，使用 `prompt` 在原进程、原会话、原轮次继续执行；处理完后才完成最终收尾和通知。这个步骤没有新建 `turnId`。

如果 `SendMessage` 在任务最终结束后才被处理，则沿用现有自动续接逻辑开启新轮次。主动停止会关闭未消费消息并清空队列；停止中的任务暂不接收新消息。由此区分“收尾前已经接受的补充”和“结束后新下达的任务”，操作入口保持不变。

## 数据和实现

继续使用 `runId → childSession → turnId`。问答正文与工具结果由 Pi Session 保存；任务状态只保留当前问题。双向通信记录集中在 `messages.json`，每轮完成记录使用 `results/*.json` 及对应 `results/*.md`。v3 运行快照增加可选 `reportPath`，v1/v2 原问答投影到 `legacy`。

`parent-messaging.ts` 负责子通信工具与 RPC 信封；`runtime.ts` 处理等待、回答、收尾输入、续接和进程释放；`message-store.ts` 保存消息证据并核对原生会话；`background-delivery.ts` 处理父会话归属、工具回执与异步通知协调、消费确认和有效未提交通知恢复；`persistence.mjs` 保存完整报告与结果快照。没有增加任务 DAG、调度服务、报告表单或业务验收状态机。

## 代码结构整理

本轮保持三个公开工具、运行快照 v3、单目录执行和消息账本格式，集中整理已验证行为的实现边界。

- 新任务资源准备归入 `task-creation.ts`，包括原生子会话、系统提示词、启动参数、provider 快照及失败清理；插件入口保留参数解析与工具调用协调。
- 正常 settled 先处理剩余输入，真正结束时分别确认进程释放和提交结果。停止、错误、清理重试沿用原控制队列和身份检查。
- `withToolDelivery()` 在交付模块内配对认领和失败释放，三个工具路径共用；结果格式直接从快照生成，前后台不再通过修改模式借用格式函数。
- `persistCompletion()` 返回确认保存的路径，保持传入快照不变。报告路径的失效与更新由运行控制器明确负责；历史读取使用只读 `RunDetails`，不假设存在活动状态的 `updatedAt`。
- 入口上下文使用 Pi 原生类型；消息解析在读取外部数据后进行字段检查，允许恢复扫描跳过无效条目。运行初始化逐项展开，历史启动配置刷新成为明确的独立步骤。

自动回归继续覆盖原有通信边界，并增加并发交付认领、全部操作失败后的单次补送、冻结快照保存、非终态不生成报告，以及报告刷新失败后当前状态撤销旧路径的验证。

复审中还复现了一处旧边界：历史已经保存为成功，最终状态写入与报告刷新连续失败后，续接会复用旧成功记录，导致失败证据随当前状态覆盖而丢失。现在续接先修复带持久化错误的旧轮历史，再开始新轮；旧状态哈希文件原位更新，同轮保持一份结果。对应故障测试在修改前失败，修复后通过。

结构变化：入口 `index.ts` 从 641 行降为 490 行，`finish` 从 125 行拆为只负责结束的 55 行；实现代码显式 `any` 从 38 处降为 18 处。统计包含空行与注释、排除声明文件、测试和依赖。实现总行数从 4,433 增为 4,556，增加来自职责分步、类型检查与失败恢复；数据文件版本和核心实体保持不变。

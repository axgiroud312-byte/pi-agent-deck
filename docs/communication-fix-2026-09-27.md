## 修改后的流程

```text
主 Agent 派发
  → 子 Agent 执行
  → 有关键疑问：SendMessage(main, wait_for_reply=true)
  → 主 Agent 收到问题并回答
  → 原子进程、原调用栈、原会话继续
  → 完整交付，释放进程
  → 主 Agent 验收，必要时 SendMessage 续接原会话
```

- 父 `SendMessage` 根据目标状态处理：运行中 `queued`、等待中 `answered`、结束后 `resumed`。显式 `Agent.resume` 复用相同续接实现。
- 子 `SendMessage` 使用 Pi RPC 的原生 UI 请求/响应通道，保留请求编号关联回答。唯一新增的运行字段为可选 `pendingQuestion: { id, message }`。
- 前台遇到问题先交还主 Agent 控制权；回答后继续执行，最终结果自动通知。普通进度独立发送。
- `reply_to` 防止过期回答或重复回答被当成新一轮任务。等待中支持停止；孤立进程恢复检查清除已失效的当前问题。
- 角色显式工作工具白名单自动附加通信工具。工具 AbortSignal 可取消等待。
- 每轮的交付文本按顺序保留，后续摘要追加。历史通知正文保持原样，以 `turnId` 识别轮次。
- 内置 worker、scout、reviewer 正文各一句职责；角色生成模板同样保持简短。任务范围写在派发内容，公共通信说明集中维护。
- 后台回执说明如何等待自动通知。主 Agent 可以处理独立工作，当前只需等待时结束本轮回复，结果会自动唤醒它。

## 数据和实现

继续使用 `runId → childSession → turnId`。问答正文与工具结果由 Pi Session 保存；任务状态只保留当前问题。完成记录仍使用每轮 `results/*.json`，原 v3 结构增加可选字段，v1/v2 原问答投影到 `legacy`。

`parent-messaging.ts` 负责子通信工具与 RPC 信封；`runtime.ts` 处理等待、回答、续接和进程释放；`background-delivery.ts` 处理父会话归属、工具回执与异步通知的去重。没有增加任务 DAG、调度服务、报告表单或业务验收状态机。

## 验证方法

- 真实父子 Pi + 本地 HTTP 受控模型：前后台派发、澄清回答、文件实际写入、完成后消息续接、历史正文在模型请求中保持原样。
- 真实 Pi + 本地受控 provider：连续提问、过期/重复回答、显式工作工具白名单、停止后续接、进度独立交付、完整报告后追加摘要。
- 状态与失败测试：同任务输入竞争、持久化失败、旧记录恢复、失联问题清理、进程退出确认、通知去重和父会话隔离。
- 在线模型在隔离临时目录执行：子 Agent 先提问，主 Agent 回答，子 Agent 写入并验证 JSON；主 Agent 消息续接后，将 phase 从 1 改为 2，再亲自读取验收。

首次在线实验虽然最终文件正确，但主 Agent 曾把 `resume` 当成收集结果的入口，产生多余轮次及一次运行中拒绝。该次只证明基本通路可用；据此补充了正向等待说明，后续实验与最终检查单独记录。

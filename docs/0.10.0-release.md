# 0.10.0 · 主 Pi 直接管理子 Pi

0.10.0 精简子 Agent 的通信和生命周期。主 Pi 进程直接持有任务控制器并管理子 Pi 的 RPC 会话，不再通过独立 Runner 和磁盘消息队列转发补充要求。

## 主要变化

### 同一个任务和子 Session

`Agent` 返回稳定的 `agentId`（TaskStop 的 `task_id` 使用同一个编号）。初始任务、运行中补充、结束后继续和问题答复都使用同一个任务编号和同一个子 Session。

每次具体执行在内部拥有独立 `turnId`，用于关联该轮的事件、问题和结果。`turnId` 不加入公开工具参数；调用方继续使用 `task_id`。

### 直接 RPC 通信

主 Pi 直接启动和监听子 Pi：

- 初始任务使用 prompt；
- 运行中的补充要求使用 `steer`；
- `steer` 在当前工具调用结束后的模型边界生效；
- 已结束任务的补充在原 Session 中开启新 turn；
- 显式停止、主 Pi 退出或 `/reload` 会结束活动控制器和受控子进程。

RPC 接受消息表示子 Pi 已接收，不等于模型已经处理。0.10.0 不提供脱离主 Pi 生命周期的持久后台执行。

### 问题必须明确对应

子 Agent 使用原有内部问题工具提交阻塞问题；主 Agent 收到包含唯一 `questionId` 的通知，子 Agent 的原工具调用继续等待答复。`SendMessage` 新增可选字段 `reply_to`：

```ts
SendMessage({
  to: "任务编号或实例名称",
  message: "明确答复",
  reply_to: "当前问题的 questionId"
})
```

只有匹配当前问题的 `reply_to` 才能解除等待。普通补充消息不能作为问题答复；过期问题 ID 不能恢复新的等待轮次。

## 工具参数

`Agent` 和 `TaskStop` 参数保持不变。`SendMessage` 保留 `to`、`message`、`summary`，只新增 `reply_to`。

工具名称和部分字段采用 Claude 风格，但本项目不声明完整 Claude Code 兼容。团队、权限模式、工作树、远程执行和持久后台协议不在本版范围内。

## 删除旧 Runner 和队列重放

0.10.0 删除独立 `runner.mjs`，也删除通过 `follow-up.json` 等持久队列在重启后自动执行补充消息的路径。

升级前的任务历史、结果和旧队列文件仍保留供查看。旧队列不会自动执行，也不会被猜测成“尚未送达”。需要继续的内容，应在升级并 `/reload` 后明确调用新的 `SendMessage`。

## Agent 数量与模型策略

插件不设置全局或角色任务数量上限。主 Agent 决定：

- 开启多少个 Agent；
- 使用哪些角色；
- 怎样拆分、排序和验收任务。

Jev 只为一个已经定义好的子任务选择模型与思考强度，不决定任务数量、角色或工作计划。

模型策略保持：

| 模型 | 可用任务 | 思考强度 |
|---|---|---|
| GPT-5.6 Sol | 仅审查 | `xhigh`、`max` |
| GPT-6 Sol | 非审查 | `high`、`xhigh`、`max` |
| GPT-6 Luna | 非审查 | `high`、`xhigh`、`max` |

GPT-6 Astra 对子 Agent 停用。关闭 Jev、显式模型、模型别名和回退路径都不能绕过策略。

## Pi 版本

0.10.0 的 peer dependency 最低版本与开发依赖统一到 Pi **0.87.1**：

- `@earendil-works/pi-agent-core`
- `@earendil-works/pi-coding-agent`
- `@earendil-works/pi-ai`
- `@earendil-works/pi-tui`

本机最终验收以这组 0.87.1 包为基线。

## 升级

1. 等当前旧版任务结束后更新扩展。
2. 在每个打开的 Pi 中执行 `/reload`。
3. 使用 `/agents` 查看保留的历史任务。
4. 对仍需继续的任务明确调用 `SendMessage`；不要依赖旧队列自动恢复。

0.10.0 创建的子任务会随主 Pi 重载结束。升级前必须等待 0.9.x 的旧任务结束；新版不会接管或迁移仍在执行的旧进程。
